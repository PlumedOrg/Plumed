# Plumed fork instructions

These instructions come from the Plumed maintainer and apply on top of [AGENTS.md](AGENTS.md) (the upstream Murmure guidelines, which still apply). Where the two conflict, this file wins.

This file was set up with Claude Code.

## 1. What this fork is

Plumed (repo: https://github.com/PlumedOrg/Plumed, frontend constants in `src/utils/plumed-links.ts`) is a fork of [Murmure](https://github.com/Kieirra/murmure) specialized for **French medical dictation**. It ports the features of the medical mode of ParakeetWeb ([live](http://parakeetweb.olicorne.org/?mode=med), [code](https://github.com/thiswillbeyourgithub/parakeet_web), usually checked out next to this repo in `../parakeet_web`) into an easy to install desktop app, so dictation works in any application of the computer, not only in a browser.

Why a fork and not upstream PRs: see [Kieirra/murmure#498](https://github.com/Kieirra/murmure/issues/498). The upstream maintainer prefers that very large rule lists (~30,000 regex rules) and medical specific post-processing live in a fork. We still want to stay as close to upstream as possible and upstream every change that is generic enough.

## 2. Mandatory at the start of every session: check upstream

**Last checked upstream commit:** `8ad2363` (docs: update roadmap)
**Date of check:** 2026-11-12

At the start of every new session, before other work:

1. `git fetch upstream` (remote `upstream` = `https://github.com/Kieirra/murmure.git`; add it if missing).
2. List what is new: `git log --oneline <last checked commit>..upstream/main`.
3. Summarize these commits to the user and recommend, per commit, merge or skip, flagging anything that touches files our feature branches modify.
4. After the user approves, merge (see section 4). Default is to merge everything: staying close to upstream is the point. To skip one commit, merge anyway then `git revert` it, so the history stays mergeable.
5. Update the commit hash, its subject and the date above, and commit that change (`docs(fork): update last checked upstream commit`).

Even if there is nothing new, update the date so we know the check happened.

## 3. Minimal-diff rules (keep upstream merges painless)

- Prefer **adding new files/modules** over editing upstream ones. Hook them into upstream code with the smallest possible change (one import, one call, one config entry).
- Never reformat, reorder, rename or "clean up" upstream code we don't need to change: every touched line is a future merge conflict.
- Never edit upstream docs other than `README.md` (fully replaced by ours) and the single pointer line at the top of `AGENTS.md`. Fork documentation goes in fork-specific files (this one, or new files).
- Upstream's mkdocs site (`docs/`, `mkdocs.yml`, `overrides/`, the `docs.yml` workflow) is deleted: it documents Murmure (`murmure` commands, docs.murmure.app CNAME). When an upstream merge touches those files, keep the deletion. Plumed's user docs will live on plumed.fr; the medical features are documented in `MEDICAL.fr.md`.
- Large data (medical regex lists, phrase boosting lists) goes in its own files, never inlined in upstream sources.
- Generic improvements (performance, bug fixes, things any Murmure user benefits from) must be written so they can be sent upstream as is: no medical-specific code mixed in.
- Exception to upstream's "no persistence" rule (`AGENTS.md`): when, and only when, the user opted in to anonymous usage statistics, aggregated counters (sums, buckets, error counts, never text or per-dictation records) and a random id are persisted in `telemetry.json` in the app data folder. Turning the option off deletes that file. Anything sent must stay on the allowlist tested in `src-tauri/src/telemetry/payload.rs`.

## 4. Branching model

Branches are created only with the user's approval. **Never open a pull request upstream**: only the user does that, by hand.

- `medmain`: our default branch, what we release (named so it is never confused with `upstream/main`). Equal to upstream + fork meta files (README, this file) + every finished feature, each merged in.
- `feat/<name>`: **one feature per branch**, branched from the upstream commit we last synced to (not from `medmain`), so that `git diff upstream/main...feat/<name>` shows exactly that feature and nothing else. This makes each feature:
    - easy to review and revert (merged into `medmain` with `git merge --no-ff`, one merge commit per feature),
    - easy to benchmark in isolation (build `upstream/main` vs `feat/<name>` and compare),
    - easy for the user to propose upstream (a PR straight from the branch).
- If a feature depends on another one (example: the medical phrase list needs the new phrase boosting engine), branch it from its parent feature branch and note the dependency in the table below.
- Syncing upstream: `git merge upstream/main` into `medmain` (never rebase `medmain`, it is published). Feature branches not yet merged: rebase them onto `upstream/main` (or merge if already shared).
- `git rerere` is enabled locally (`git config rerere.enabled true`) so a conflict resolved once is resolved automatically next time.
- Recurring conflicts and how to resolve them:
    - `README.md`: always keep ours.
    - Version fields (see section 5): always keep ours.

Removed upstream features (security, for hospital use): the local HTTP API, Command mode, and Prompt mode (LLM Connect: Ollama, remote LLM servers and their keyring API key, SmartMic LLM and translation modes, LLM and command wake words). SmartMic is removed too (phone as microphone over the LAN through a local HTTPS/WebSocket server and its relay settings, its phone page and `build:smartmic` step, its settings and export category, its telemetry flag): the relay-based remote microphone replaces it. Old settings files and `.murmure` exports that still contain `smartmic_*` keys or a `smartmic` category load as before, those keys are ignored. Voice mode is removed as well (wake word listening, its page, toggle shortcut, `--voice-mode` CLI flag, settings, export category, telemetry flag, and the overlay mode flash it was the last user of); old settings files and `.murmure` exports with `wake_word_*`, `silence_timeout_ms`, `voice_mode_toggle_shortcut` keys or a `voice_mode` category still load, those keys are ignored. The upstream "Getting started" checklist (sidebar card, its `onboarding` settings key, commands and focus tracking) is removed too, as clutter for the medical audience; old settings files with an `onboarding` key still load. The startup prompts and the Wayland help cards under `src/features/onboarding/` stay. This is a deliberate exception to the minimal-diff rules: when merging upstream, keep these features out and resolve conflicts in their files by keeping them deleted.

Note for `feat/medical-regex`: the `feat/regex-compile-once` cache (capped at 4096 patterns) is sized for user rules, including the 138 InterHop rules seeded by default. The ~42,000 drug and term rules do not use it: `src-tauri/src/medical/` indexes them by anchor word at startup and compiles each rule lazily, the first time a text could match it.

Note for `feat/phrase-boosting`: benchmarked on 200 UltiMed validation clips (ParakeetWeb's `benchmark_datasets/french_medical/`, padded with 0.25 s of silence like the app does; unpadded clips drift into English and give meaningless numbers). WER without boosting 12.3% (drugs) / 13.1% (dictionary). Upstream's boost fed the ~77k medical phrases raises it to 17.6% / 18.5%: its strength and rank gate suit a few user words, not a huge list. ParakeetWeb's trie with the list lowers it to 12.0% / 11.7%. Hybrid with the dictionary on top: 11.6% / 12.0%, and the most target terms recovered. The ignored test `phrase_boost::model::tests::bench_transcribe` is the harness.

Note on the decoder (`src-tauri/src/engine/beam.rs`, ported from ParakeetWeb's `parakeet.js` with Claude Code): final transcriptions use a TDT beam search, MAES with width 5, 2 expansion steps, beta 2, gamma 2.3, prefix search alpha 1. Duplicate hypotheses merge with log-sum-exp, each frame prunes by raw score, and the final pick is length normalized. A step scores the true token log-probability plus the boost bonus (boosted minus raw logit) plus the duration log-probability; candidates are ranked by boosted logits. Every hypothesis advances its own decoder state, dictionary boost state and phrase trie active set. `ParakeetInferenceParams::beam_width` selects the width (default 5); the streaming preview asks for `ParakeetInferenceParams::greedy()`, and width 1 runs the original greedy decoders unchanged. The boost divergence guard still compares against unboosted greedy (cheap), then reruns unboosted at the requested width. Benchmark: `PLUMED_BEAM_WIDTH` in `phrase_boost::model::tests::bench_transcribe`, on ParakeetWeb's 4 French medical sets (400 clips) with its medical phrase list, normalized like ParakeetWeb. UltiMed model: WER 4.08% greedy, 4.05% beam 5 (dictionary 3.00/3.00, drugs 3.92/3.48, parhaf 4.44/4.51, parrot 4.53/4.55); decode time 0.163 vs 0.309 s per audio second (machine under a load of about 20 from other jobs, so timings are noisy). ParakeetWeb's ultra model, for comparison with its own run: 8.46% greedy, 7.90% beam 5 (ParakeetWeb: 8.26% and 7.80%), so the beam gain matches; it is small with UltiMed, already fine-tuned on this domain. The joint calls are batched like ParakeetWeb's: one decoder_joint run per MAES expansion step, one for the blank closures and one per prefix search step (`Parakeet::decode_steps`). Rerun after batching on the same loaded machine: greedy 4.08% at 0.218 s per audio second, beam 5 4.06% (drugs 3.45) at 0.241 s, so beam 5 now costs about 1.1x greedy instead of 1.9x; the 4.05 to 4.06 shift is float rounding in the batched runs. ParakeetWeb's own harness on the very same UltiMed v1 int8 files (wasm, same boost settings): 4.13% greedy, 4.05% beam 5 (drugs 3.86/3.33), so both decoders agree within noise. Rerun on the v2 model (Claude Code, 2026-11-23; UltiMed v2 Ultra int8, ONNX Runtime 1.31, the 400 held-out v2 clips of the boost tuning note below, weight 0.5, commitment 0.5): WER 2.97% greedy, 2.82% beam 5 (dictionary 2.34/2.10, drugs 3.11/2.69, PARHAF 2.51/2.46, PARROT 4.03/3.94), same peak RSS (about 2.1 GB); decode time 0.190 vs 0.355 s per audio second, on a machine loaded by other jobs, so the cost ratio (1.9x here, 1.1x in the run above) is noisy.

Note on the phrase boosting tuning on v2 (written with Claude Code, 2026-11-22): the v1 tuning (weight 1.5, min-p 0.01, commitment 0) made the v2 model worse than no boosting. Scored with the v2 labels on the 117 clips of ParakeetWeb's benchmark that are in v2's validation or test splits (183 of its 300 non-PARROT clips are in v2's training split, and its manifests still carry the v1 labels), beam 5, WER: no boost 3.45, v1 tuning 3.70; sweep weight {0.5, 0.75, 1, 1.5} x commitment {0, 0.5, 0.75, 1} x min-p {0.01, 0.1}: lower weight and commitment around 0.5 to 1 win, a plateau at 3.21 to 3.25 for weight 0.5 to 0.75 and commitment 0.5 to 1. Then on ParakeetWeb's french_medical benchmark regenerated on 2026-11-22 from the v2 corpus (`gen-medical-val-sets.mjs`, seed 1234, v2 val splits and PARROT test, 400 clips, none in a v2 training split, v2 labels), WER overall: no boost 3.03, v1 tuning 3.33, weight 0.5 commitment 0.5 2.79, weight 0.75 commitment 0.5 2.84, weight 0.75 commitment 1 2.78, weight 1 commitment 0.5 2.89. Chosen: weight 0.5, commitment 0.5, min-p 0.01 (2.79 here, 3.23 on the 117 clips), the most consistent over both sets. Per set (dictionary, drugs, PARHAF, PARROT): 2.06, 2.72, 2.37, 3.96 against 2.34, 3.34, 2.56, 4.06 without boost. The v2 "drop" against v1 seen on the full 400 clips was mostly the label conventions: v2 writes "1" for "un/une", "postopératoire" without hyphen and "80000" without space, as the v2 labels do, while the references keep the v1 spellings.

Note on the confusion-group second pass (`src-tauri/src/engine/confusion.rs`, written with Claude Code): after the beam search, a decoded word listed in UltiMed's `confusion_groups.jsonl` (heard form with several possible targets, 68 of the 415 groups of v2.0.2 kept; the benchmark below ran on the 905 groups of v2.0.0) is re-scored on its encoder frames together with the previous word: best TDT alignment of each candidate from the unboosted log-probabilities, one batched decoder call per frame. It replaces the word only when a candidate scores higher. Built-in option "Resolve sound-alike medical words", final transcriptions only. Benchmark on the v2 model (`PLUMED_CONFUSION` in `bench_transcribe`): on 233 held-out confusion cases (test split of the rules mining), margin 0 fixed 6 (Förster, intraorbitaire x3, rétinoïdes, triptan) and broke none, margin 1 fixed 1, margin 2 none; on the 400 general clips margin 0 left every output unchanged. Default margin 0.

## 5. Versioning

Plumed has its own version number, independent from upstream's, starting at `0.1.0` (semver: Cargo, `package.json` and Tauri all require three numbers, optionally followed by a pre-release suffix such as `0.2.0-beta.1` for beta releases, see section 6). Semver orders `0.2.0-beta.1` < `0.2.0-beta.2` < `0.2.0`, so a beta user gets the final release. Caveat: the Windows MSI (WiX) only accepts a numeric pre-release, so `build-windows.yml` builds the NSIS installer alone when the version contains `-` (the updater and winget use NSIS anyway). The auto-updater compares it with the `version` in `latest.json`, so every release must bump it. Upstream's version is not tracked in ours: the last merged upstream commit is recorded in section 2.

The version must be identical in `package.json`, `src-tauri/Cargo.toml` (and `Cargo.lock`) and `src-tauri/tauri.conf.json`. When an upstream merge conflicts on these lines, keep ours.

Ship the NSIS `-setup.exe` as the main Windows installer: it installs without admin rights, and `latest.json` points Windows updates to it.

## 6. Releases

Identity: the app identifier is `org.olicorne.plumed` (own settings and history folder, separate from an installed Murmure). The product name is `Plumed` and the binary `plumed` (`mainBinaryName`), so Plumed installs next to Murmure: Linux package `plumed`, `/usr/bin/plumed`, resources, ONNX Runtime and the pacman marker in `/usr/lib/Plumed/` (the binary's rpath, set in `build-linux.yml`, points there), udev rule `60-plumed-uinput.rules` (not shipped in the packages, see section 7), release files `Plumed_*`. Upstream's crate names (`murmure`, `murmure_lib`) and the `.murmure` config import format are kept.

ONNX Runtime (written with Claude Code): the `ort` crate is pinned at `2.0.0-rc.15`, which targets ONNX Runtime 1.31.0. Sessions share one environment created with telemetry off (`ort_environment` in `engine/engine.rs`). Linux CI (`build-linux.yml`) takes `libonnxruntime.so` from Microsoft's official NuGet package `Microsoft.ML.OnnxRuntime` 1.31.0 (SHA-256 pinned) because `github.com/microsoft/onnxruntime` answered 404 at the upgrade (2026-11-23), so the release tarballs and the source were unreachable. Windows and Apple Silicon use the binaries `ort` downloads (`download-binaries`). The Intel Mac build compiles v1.31.0 from source with `.github/ort/0001-mlas-avx2-without-avxvnni.patch`, which was written for 1.23.2 and could not be checked against 1.31.0 (TODO in the workflow); its VNNI detector is still calibrated on Microsoft's 1.23.2 build. Both Mac steps need GitHub to serve `microsoft/onnxruntime` again. To bump ONNX Runtime, update the version and checksum in `build-linux.yml` and `build-macos-intel.yml`.

Auto-updater (written with Claude Code; `src-tauri/src/app_update.rs`, key and stable endpoint in `plugins.updater` of `src-tauri/tauri.conf.json`): the check and the install run in Rust through `updater_builder().endpoints(...)`, the frontend (`update-checker.tsx`) only calls `check_app_update` / `install_app_update`. The setting "App updates" (`app_update_channel`, Settings > Online, also set by the `set_app_update_channel` command for a future first-launch wizard; never exported) has three values:

- `stable` (default, also for users from before the setting): `latest.json` of the latest release (`/releases/latest/download/latest.json`, which skips pre-releases).
- `beta`: the GitHub API listing of the 10 newest releases; the newest one that is not a draft and ships a `latest.json` asset wins (pre-release or not), and its `latest.json` URL is built from the tag.
- `disabled`: no check at startup; the sidebar button then checks the stable channel on demand. With the other two the button only appears when an update is available.

The updater only installs a version greater than the running one, so going back from beta to stable never downgrades: a `0.2.0-beta.3` user waits for `0.2.0`. Relay fallback: when any request to GitHub fails (network error, timeout, or an HTTP error such as a proxy's 403), the check is retried through the model relay (`models.plumed.fr`, `relay_base()` in `model/download.rs`, same override as the models), whose `/releases/...` routes mirror the GitHub paths minus `/PlumedOrg/Plumed` (`remote_microphone_server/protocol/src/releases.rs`, routes in `remote_microphone_server/README.md`); the installer URL of the update is then rewritten to the relay too, and a failed installer download from GitHub is retried through the relay. A relay cannot forge an update: whatever it serves, the app installs only an installer whose minisign signature matches the `pubkey`. One-time setup:

1. `pnpm tauri signer generate -w ~/.tauri/murmuremed.key` (asks for a password). It writes the private key `murmuremed.key` and the public key `murmuremed.key.pub`. Keep the private key out of the repo and back it up: if it is lost, installed copies can never be updated again.
2. Paste the content of `murmuremed.key.pub` as `pubkey`.
3. In the GitHub repo settings (Secrets and variables > Actions), add `TAURI_PRIVATE_KEY` (the output of `base64 -w0 ~/.tauri/murmuremed.key`: the workflows decode it with `base64 -d` before signing, so the raw file content does not work) and `TAURI_KEY_PASSWORD`. The build workflows use them to sign the bundles (`.sig` files next to each installer).

Each release: bump the version (section 5), run the `Release Plumed` workflow, create a GitHub release tagged with the version (for example `0.1.0`, or `0.2.0-beta.1` marked as a pre-release on GitHub for the beta channel) from its artifacts, then run `python scripts/make-latest-json.py <artifacts folder> --notes "..."` and upload the `latest.json` it writes. Every release, beta included, must carry its `latest.json`: the beta channel skips releases without one. That file lists, per platform, the installer URL and the content of its `.sig` (format: https://v2.tauri.app/plugin/updater/#static-json-file); the workflows do not generate it.

Code signing: there will never be an Apple developer account, so macOS builds are unsigned and not notarized (users must allow the app in System Settings > Privacy & Security, or run `xattr -dr com.apple.quarantine /Applications/Plumed.app`); the macOS workflows run their Apple certificate, DMG signing and notarization steps only when the `MACOS_CODESIGN_P12_B64` secret exists, and otherwise ad-hoc sign the `.app` (`APPLE_SIGNING_IDENTITY=-`), which Apple Silicon requires to run it at all. Windows: the SignPath step runs only when `SIGNPATH_API_TOKEN` exists; otherwise the installers are released unsigned (SmartScreen warning). Either way the Tauri updater signature (`.sig`) is always made.

WinGet (`.github/workflows/publish-winget.yml`, id `Olicorne.Plumed`, NSIS `-setup.exe` only): it runs on every published release, but it can only update a package that already exists in microsoft/winget-pkgs. The first version must be submitted once by hand (for example with `komac new` or `wingetcreate new`), then add a `WINGET_TOKEN` secret (a GitHub token allowed to open PRs on winget-pkgs).

Usage statistics (opt-in, `src-tauri/src/telemetry/`, section written with Claude Code) are configured at build time through two environment variables read with `option_env!`:

- `PLUMED_TELEMETRY_WEBSITE_ID`: the Umami website id. Every workflow that runs `tauri build` passes it from the GitHub Actions **repository secret** of the same name (`${{ secrets.PLUMED_TELEMETRY_WEBSITE_ID }}`, set on 2026-11-21). When it is unset or empty, telemetry is inert: no consent dialog, no setting, nothing sent. A due send waits a random delay of up to 15 minutes, so its time reveals neither the launch nor the opt-in nor the use.

Server side (VPS, set up on 2026-11-21): Caddy proxies only `POST metrics.plumed.fr/api/send` to Umami (`localhost:3823`), with its own access log `/var/log/caddy/metrics-plumed.log` (named logger `metrics_plumed` with `log_name`, so these requests never reach the shared `access.log`; full IPs, mode 0600, rolling disabled) pruned to the last 24 hours by the hourly root timer `caddy-prune-metrics-log.timer` (`/usr/local/sbin/caddy-prune-metrics-log.py`, rewrites the file in place); every other path answers 404. The privacy policy states this 24 h log. Umami has no retention setting, so the root timer `umami-purge-plumed.timer` runs `/usr/local/sbin/umami-purge-plumed.sh` daily: it deletes the Plumed website's rows older than 25 months from every Umami table that has a `website_id` (events, event data, sessions with no event left, ...). `RETENTION='0 seconds'` runs it as a test.

- `PLUMED_TELEMETRY_URL` (optional): the Umami 3 collect endpoint, default `https://metrics.plumed.fr/api/send`. Not passed by the workflows on purpose (an empty variable would override the default); set it only for local test builds.

Medical data updates (fork only, section written with Claude Code): the drug and medical term rules, the confusion groups and the phrase list can be updated online without an app release. Code: `src-tauri/src/medical/data_set/` (the one place that knows whether the bundled or a downloaded set is in use: manifest checks, on-disk sets, fallback to the bundled data), `src-tauri/src/medical/data_update.rs` (startup check, download, install), `src-tauri/src/commands/medical_data.rs`, frontend in `src/features/medical-data/` and `src/features/onboarding/` (`startup-wizard/steps/medical-data-step.tsx` asks on first launch, `medical-data-prompt/` offers an update and waits for a launch where the startup wizard does not open). Manifest format, checks and storage: the "Online updates" section of `src-tauri/medical-data/SOURCE.md`.

- Consent: no check, so no network call, before the user answered the first launch question ("Ne pas vérifier" / "Vérifier à chaque démarrage", shown on a launch without the PhoneMic or usage statistics question; installs from before the question are asked once too). The answer, or the settings toggle, sets `medical_data_update_check` and `medical_data_update_asked` (both never exported). A "yes" checks from the next start on, so no second dialog shows that launch.
- Flow: once per launch, at startup and only when the user agreed to the check, the app fetches `manifest.json` and its signature from the `medical-data` release (plain GET, user agent `Plumed`, no identifier, no cookie). A valid, newer, not skipped set opens a dialog (Not now / Skip this version / Download); nothing is downloaded without that click. After the download the drug rules and the engine lists switch live. The user's edits are never touched, edits of rules that no longer exist are kept and marked in the rules editor. The Online tab of Settings > System (`src/features/settings/system/online-settings/`, the one place `MedicalDataSettings` is shown; the Corrections Explanation tab only shows the version in use and links there) shows the version in use, the toggle, the last check of this launch (date and result, kept in memory only), "Check now", "Install a downloaded update" and "Return to the bundled data".
- Failed check (network error, GitHub blocked, timeout, bad signature...): the backend keeps the error and the frontend takes it once per launch (`take_medical_data_check_failure`), showing a toast with a link to the `medical-data` release page (opened in the system browser, which hospital networks sometimes allow when the app is not) and the manual install hint.
- Manual install: the user picks the release assets downloaded by hand (`manifest.json`, `manifest.json.minisig` and the data files; multiple file selection, which works on all three OSes, other picked files are ignored). Same checks and install code as the online update: `data_set::checked_manifest` (signature, allowlist, sizes, hashes, model, `min_app_version`, newer), `data_set::StagedFile` (size and SHA-256 of each file as it is written) and `install_in`. - Failsafe (beyond signature, allowlist, hashes, sizes, model and version): a set is also refused, and the data in use kept, when more than 5% of its rules do not parse, when its phrase list or confusion groups have less than half the bundled entries (truncated publication), or when its rules rewrite more than 8 sentences beyond what the bundled rules rewrite on `medical-data/canary/correct_sentences.txt` (the labels of the 400 held-out benchmark clips: correct text no rule should touch). Every check runs again on the installed set at each launch; any failure falls back to the bundled data, never to a partial set.
- Key: the manifest is signed with a dedicated minisign key (not the Tauri updater key). Create it once with `minisign -G -p plumed-rules.pub -s ~/.minisign/plumed-rules.key` and keep the secret key out of the repo. The base64 line of `plumed-rules.pub` goes in the `PLUMED_RULES_PUBKEY` **repository secret**, which every workflow that runs `tauri build` passes as an environment variable, read with `option_env!` in `src-tauri/src/medical/data_set/mod.rs`. When it is unset or empty the feature is inert: no network call, no dialog, no setting shown. The key pair was created and the secret set on 2026-11-21 (the maintainer keeps both files in `~/.minisign/`).
- Publishing: `scripts/publish-medical-data.sh <version> "<notes>"` (signs with `PLUMED_RULES_KEY`, default `~/.minisign/plumed-rules.key`, and uploads to the `medical-data` prerelease, created with `--latest=false` so it never hides the app's `latest.json`). Bump `BUNDLED_VERSION` in `data_set/mod.rs` whenever the bundled files change, and `MODEL_ID` when the model changes (old sets are then refused).

Speech models (fork only, section written with Claude Code): the app does not bundle its speech model. On first launch the first step of the startup wizard (`src/features/onboarding/startup-wizard/steps/model-step.tsx`) offers the catalog and downloads the chosen variant once into `<app data>/models/`, outside the install folder, so updates keep it. - Catalog (`src-tauri/src/model/catalog.rs`): UltiMed v2 Ultra int8 (668 MB, WER 2.82 %, peak RSS 2.07 GB) and Ultra w4a8 (402 MB, WER 2.87 %, peak RSS 1.69 GB), both at revision `675b4b8`, with every file's size and SHA-256 compiled in. Redux w2a8 (294 MB) is listed as "bientôt disponible" and cannot be picked: ONNX Runtime 1.31 runs it, but its WER is 5.04 % for a peak RSS of 1.47 GB, so it stays off (TODO in the catalog). Figures from `bench_transcribe` on the 400 held-out clips with the boost at weight 0.5 and confidence 0.5, under ONNX Runtime 1.31 (measured with Claude Code; under 1.23 int8 scored 2.79 % and w4a8 2.88 %, the difference is single word near-ties).
- Recommendation (`catalog::recommended`, `model/memory.rs`, written with Claude Code): below 8 GiB of total RAM (`sysconf` on Linux and macOS, `GlobalMemoryStatusEx` on Windows) the lightest available variant is recommended, otherwise the first; unknown RAM keeps the first. `get_model_status` returns it as `recommended`, and the chooser preselects it (when nothing is active, downloading or installed) and marks it "Recommandé". The threshold's reasoning is in the comment of `LOW_MEMORY`. Every variant installs under the file names the engine loads (`encoder-model.int8.onnx`, `decoder_joint-model.int8.onnx`, `nemo128.onnx`, `vocab.txt`, `config.json`). The repositories and revisions live in `remote_microphone_server/protocol/src/models.rs` (`MODEL_REPOS`), shared with the relay; a test checks the catalog only uses them.
- Store (`store.rs`): one folder per variant and revision (`ultra-int8-675b4b8d7ee9/`), `.partial` files while downloading, a `model.json` marker written last, `active.json` naming the variant in use. Launch does a cheap check (marker and sizes); if the engine then fails to load, a full hash check runs and a damaged model is dropped, which opens the dialog instead of crashing. Folders of other revisions are removed after a successful download.
- Download (`download.rs`, `manager.rs`): Hugging Face first (redirects followed only to its https hosts), then the Plumed relay `https://models.plumed.fr/models/<repo>/<path>?revision=<commit>` (`remote_microphone_server/models/`, for hospital networks that block huggingface.co). Range resume of each `.partial`, 3 attempts per source with backoff, cancel, progress events with a smoothed speed, a free disk space check, then size and SHA-256 checks and an atomic rename. One download at a time. Errors are a typed `DownloadError` the frontend explains in French (`downloadErrorMessage`).
- `PLUMED_MODEL_RELAY_URL` (optional, build time, `option_env!` in `download.rs`): another relay base URL, default `https://models.plumed.fr`. The build workflows pass the GitHub Actions **repository variable** of the same name (`${{ vars.PLUMED_MODEL_RELAY_URL }}`); unset or empty keeps the default.
- Recording with no model shows the main window, a "Aucun modèle téléchargé" toast and the wizard on its model step (`model-missing` event). The model step is always the first one (`getDueSteps` in `startup-prompts.helpers.ts`), and the download keeps running in the backend while the next steps are answered. The usage statistics `model` field is the active variant id (`dev` or `none` otherwise).
- Development: debug builds fall back to `resources/parakeet-tdt-0.6b-v3-int8/` while no model is downloaded, so run `bash scripts/fetch-ultimed-model.sh` once (it also serves `engine::beam`'s ignored test). Release bundles list their resources explicitly (`tauri.conf.json`), so that folder never ships. CI no longer fetches the model, except the Intel macOS smoke test, which installs it in the app data folder with `--models-dir`.
- Adding a model: publish it on Hugging Face with the same file layout, add its repository and revision to `MODEL_REPOS`, add the variant with sizes and hashes to `catalog.rs`, keep the old revision in `MODEL_REPOS` while released apps still download it, and redeploy the relay. When the model family changes, bump `MODEL_ID` too (medical data sets are tied to it).
